# Benchmark methodology (Pandas vs PySpark, local mode)

All benchmark data are **synthetic**, generated by `backend/app/benchmark/generate.py` with a fixed seed
(`SeedSequence([seed, rows, regions])`), so the same settings give a byte-identical file. They are not Sentinel-2 observations and
say nothing about environmental results. Spark runs in **local mode on one machine**; nothing here indicates cluster performance.

## Question
For the same grouped-aggregation workload on tabular index data, how do Pandas and PySpark (local mode) compare in processing time on this machine, and do they agree numerically?

## Dataset
Columns: `observation_id, region_id, observation_date, ndvi, ndwi, ndbi, valid_pixel_count`. Sizes: 100,000 / 1,000,000 / 5,000,000 rows
(5M only if memory permits; the API refuses runs whose estimated memory exceeds 70% of available RAM, and 1M+ needs explicit confirmation).
About 2% null indices, 1% out-of-range values and 3% zero pixel counts are injected so the filter has work to do.

## Workload (identical logic in both)
1. Filter: all three indices non-null and within [-1, 1], `valid_pixel_count > 0`.
2. Annual summary by (region, year): counts, pixel sum, mean NDVI/NDWI/NDBI, sample SD, min, max, pixel-weighted mean NDVI.
3. Regional summary by region over the valid raw rows.
4. Annual change vs previous year (only when the gap is exactly one year).
5. Write three Parquet tables.

## Timing and metrics
* **Processing time (per trial)** = read Parquet + filter + aggregate + window + write Parquet. **Excluded**: data generation (reported separately), framework start-up (`init_s`, reported separately), warm-up runs.
* Each framework runs in its **own subprocess**; `warmup` runs are discarded, then `trials` measured runs are recorded individually; the **median** (plus min, max, mean, SD) summarises them.
* **Throughput** = input rows / median processing time.
* **Speedup = Pandas median / PySpark median.** Above 1 PySpark was faster; below 1 Pandas was faster. Stored only when both completed and agreed.
* **Peak memory**: sampled (50 ms) resident memory of the process tree including the JVM. Approximate; not directly comparable between frameworks.
* Recorded per run: Python, Pandas, NumPy, PyArrow, PySpark and Java versions, OS, CPU count, memory, Spark settings, timestamps, actual and valid row counts, output rows and bytes.

## Correctness
Outputs are sorted by key and compared: counts, years and pixel sums **exactly**; floats with `|a-b| <= 1e-12 + 1e-9*|b|`; null positions must match.
MAE and maximum absolute error are reported. A mismatch marks the benchmark **failed**, stores no speedup, and is never hidden.
If Spark cannot start (for example Java missing), the run is recorded as failed with the cause; Pandas is **never** substituted for Spark.

## Measured results (sandbox; synthetic data; seed 42)
Machine: 2 logical CPUs, 8 GB RAM, Linux; Python 3.11.17, pandas 2.3.3, PySpark 4.2.1, Java 21.0.12, `local[*]`, 1 warm-up run.

| Rows | Trials | Pandas median s | PySpark median s | Speedup | Spark init s | Peak RSS MB (Pandas / Spark) | Agreement |
|---:|---:|---:|---:|---:|---:|---:|---|
| 100,000 | 5 | 0.066 | 2.568 | 0.026 | 10.1 | 199 / 1128 | PASS (max err 2.8e-15) |
| 1,000,000 | 3 | 0.358 | 4.455 | 0.080 | 10.4 | 463 / 1016 | PASS (max err 1.0e-14) |
| 5,000,000 | 3 | 1.954 | 10.331 | 0.189 | 10.4 | 1471 / 1490 | PASS (max err 1.4e-14) |

## Interpretation
On this 2-core machine, for this workload and these sizes, Pandas was faster at every size. The gap narrows with size, consistent
with Spark's fixed overhead being amortised, but three sizes on one machine do not show whether or where a crossover occurs.
Spark's advantages (data larger than memory, many nodes) are not tested here. Do not quote these numbers for other hardware: rerun on yours.

## Limitations
3-5 trials per size and no significance testing; heuristic memory estimate calibrated on three measurements; on Windows without `winutils.exe`, `spark_write=auto` falls back to a labelled `collect` write (Spark collects the small result tables and PyArrow writes them), which changes what Spark's time contains; the effective mode is stored with each run; small test datasets prove correctness, not performance.

## Windows 11: Java and PySpark
Spark 4.x documents Java 17 or 21. Check `java -version`; install a JDK (e.g. Eclipse Temurin 21) and set `JAVA_HOME` to the folder containing `bin\java.exe`:
```powershell
$env:JAVA_HOME = "C:\Program Files\Eclipse Adoptium\jdk-21.0.x-hotspot"
$env:Path = "$env:JAVA_HOME\bin;$env:Path"      # this terminal; use setx JAVA_HOME ... for new terminals
python -m app.benchmark.cli --rows 100000 --trials 5 --warmup 1   # run from backend\, no database needed
```
`GET /api/benchmarks/preflight?rows=N` reports Spark availability and the exact reason when unavailable. See backend/README.md for details.
